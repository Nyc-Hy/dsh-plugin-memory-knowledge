# 记忆与项目知识产品设计

状态：产品方向已确认，评审补充已纳入设计，待实现。本文定义产品行为；[知识生命周期与实施设计](knowledge-lifecycle.md)定义完成检查、版本、修订、同步和验收要求，不表示现有运行时已经支持这些行为。

日期：2026-09-09

本文优先于[既有设计与实现基线](design.md)中的混合入口、混合召回和知识逐卡审核规则。当前安装与运行行为仍以[运行说明](runtime.md)及代码为准。

## 1. 产品划分

记忆保存跨任务应遵守或借鉴的偏好、约束、经验、方法与决策；知识解释一个项目的业务、实现和运行关系。两者具有独立入口、记录类型、检索接口和模型上下文，不因为共用数据库或证据组件而混合展示。

```text
记忆
  个人记忆
  项目记忆 → 选择项目

知识 → 选择项目
  项目 Wiki：面向用户的文章、业务流程、代码导航
  Agent 知识：面向分析的结构化知识及其可视化检查
```

知识的两个 Tab 读取同一份项目知识和同一个版本。分析进度、来源、预算与历史放在项目内的辅助面板，不占用第三个知识 Tab。没有正式知识时，两种视图都可以查看分析草稿；Agent 的默认检索接口不读取草稿。

## 2. 记忆

个人与项目记忆采用同一套分类，再通过标签细分领域。

| 分类 | 个人记忆示例 | 项目记忆示例 |
|---|---|---|
| 偏好 | 默认中文、偏好的回答详略 | 项目文档语言、常用表达约定 |
| 约束 | 修改与提交的授权约定 | 接口变更要求、兼容性要求 |
| 经验与踩坑 | 环境问题的排查经验 | 数据迁移、缓存或部署的已知风险 |
| 方法与流程 | 常用排查与验收步骤 | 发布流程、故障处理步骤 |
| 决策与理由 | 工作方式的选择依据 | 架构取舍与被放弃方案的原因 |

每条记忆包含标题、内容、分类、标签、适用范围、适用条件、来源、创建与修改时间、状态及替代关系。经验的前提与版本条件不能在压缩时丢失。新旧条目冲突时保留可追溯的替代或冲突关系，支持编辑、废弃、删除和恢复历史版本。

个人/项目描述适用范围，本机私有/Git 共享描述可见性，二者独立。项目记忆可以先只在本机使用，再由操作者显式共享给团队。个人记忆使用独立的长期条目，不把已接受候选本身当作唯一长期存储模型。项目在多个 Workspace 或多台机器间使用稳定项目身份，Workspace id 和绝对路径仅作为本机映射。

自动对话提取、候选审核、长期记忆生效和团队共享分别记录状态。知识的自动可用规则不自动改变记忆候选的审核策略。记忆纠正后，新请求不得继续召回已替代正文，已记录 Session 的历史召回保持不变。

第一版中，对话自动提取和模型推断均先进入候选；用户在记忆编辑器中明确新建或修改并保存，则直接形成生效的长期条目。个人记忆默认且仅支持本机私有；需要分享的内容经过脱敏和明确确认，另存为项目记忆，不将个人库整体导出。项目记忆的本机生效与 Git 共享是两个独立动作。失效、废弃和删除条目退出默认召回；删除保留可恢复的修订历史，彻底清除敏感数据另行处理，不能承诺抹去已有 Git 或 Session 副本。

记忆中的约束有明确的提出者与适用范围，不因被模型生成或召回就提升为系统指令或工具授权。项目约定与当前实现也必须区分：例如“接口要求幂等”属于记忆，“当前接口怎样实现幂等”属于知识；两者可以互相引用。

记忆冲突先判断适用条件是否重叠，再判断是否属于同一类主张。项目约束与代码现状不一致时同时展示要求和现状；两条同范围约束冲突时提示澄清，不仅凭最新时间或检索分数选一条。尚未解决的冲突需要成组召回，预算放不下双方时只返回冲突提示，不能只返回一方正文。

记忆可视化以分类列表和单条详情为主：展示来源对话或可共享说明、适用条件、修订时间线、替代/冲突关系、关联项目知识，以及最近实际注入模型的召回记录。来源不可访问时明确提示，不暴露私有 Session；“已召回”不代表模型实际遵循。关系按当前条目局部展开，不以全库大图作为首版前提。

## 3. 项目知识与两个视图

项目知识必须由对项目材料的完整深度 Wiki 分析形成。文件清单、AST 符号、静态模块边和原始搜索结果是分析材料或导航，不能独立晋升为已完成的项目知识。源码检索可以在 Wiki 完成前工作，但应明确返回原始材料而非正式知识。

项目 Wiki 按业务问题组织连贯说明，包含项目目标、业务术语、核心实体、业务规则、正常与异常流程、模块职责、数据与接口，以及可定位的实现和测试。流程的每个步骤、条件、状态变化和跨模块关系都应能查看对应证据；代码不能确定的业务意图保留未知或引用操作者补充。

Agent 知识以实体、规则、流程步骤、模块和关系为查询对象，支持按问题定位、逐层展开、影响范围分析和证据回查。返回内容包含项目版本、来源、确定程度、过期标记与省略信息，按请求预算装配上下文，不注入整本 Wiki。用户在该 Tab 能检查 Agent 可用的事实、关系和查询结果，不展示模型内部推理过程。

同一语义对象使用稳定 id；文章、流程图、代码导航与 Agent 查询引用该对象。页面标题、位置或分析 Run 变化不应改变人工修订所关联的对象身份。普通文字说明与可执行查询所依赖的事实、规则和关系分开建模，但共享项目知识版本。

记忆与知识可以通过明确的对象引用关联查询。例如“幂等要求是否落实”应同时找到记忆中的约束与知识中的实现/测试，并分别说明来源、版本及是否有证据支持满足要求。关联展开遵守项目范围、可见性和总预算，不合并两个领域，也不把“有关联”当作“已经符合约束”。

## 4. 分析、完成与自动可用

```text
建立分析范围 → 阅读与分层综合 → 业务流程串联 → 回查与覆盖核验
                    ↓ 可随时查看草稿
全部必需阶段完成 → 自动激活项目知识版本 → 用户阅读 / Agent 使用
                                             ↓
                                        用户修改并保存
                                             ↓
                                       新修订立即生效
```

“完成”是完整深度分析的完成，不是单个模型请求成功或所有现有分片任务退出。该运行必须绑定明确的 Source 版本与范围，完成纳入范围的材料分析、核心业务问题与跨模块流程综合、必要的引用及一致性核验，并产出两个视图需要的知识对象。排除项必须有原因；遗漏、失败任务和耗尽预算不能被静默改成排除项以满足完成条件。

系统保存版本化的分析清单和完成报告：逐项记录材料覆盖、业务问题、跨模块流程、回查任务及其结果。业务问题至少覆盖入口、实体、规则、正常/异常路径、数据和外部依赖；不适用项要说明原因。未知必须记录已经调查的材料、仍缺少的证据和影响，未阅读或预算中断不能记为“已调查但未知”。操作者可以另建缩小范围的分析，但系统必须标明局部知识，不能据此宣布全项目完成。具体检查见[完成标准](knowledge-lifecycle.md#2-完整深度分析的完成标准)。

材料覆盖必须能关联原文区间、实际送入模型的请求消息及分析结果；本地扫描完成但只把摘要交给模型不算完整阅读。旧 Wiki 和记忆可以作为分析线索，不能代替原始证据反复证明自身结论。该记录证明材料交付和分析过程，不证明模型语义零误差。

分析完整性与结论确定程度是两个独立维度。充分分析后仍然无法确认的业务问题、推断和冲突应保留具体状态，不要求所有条目都成为 verified 才能使用知识。若关键问题尚未得到必要的分析，运行仍未完成；若已分析但来源本身矛盾，可以完成并呈现冲突，Agent 不能把其中一方当作确定事实。

深度分析成功完成后，系统自动激活一个完整项目知识版本，无需用户点击审核、批准或逐卡接受。该版本的用户视图和 Agent 视图同时生效。索引或投影尚未准备好时不得提前切换当前版本；失败不得留下两种视图分别指向新旧版本的状态。

产品的最终成功状态是“完成，可使用”。内部分析已完成但索引仍在准备时显示“分析完成，正在准备知识”；准备失败时显示“知识准备失败”，不能显示可使用或要求人工审核来绕过失败。准备和激活不调用 LLM，也不增加出域确认步骤。

首次分析未完成时，项目只提供明确标记的草稿。后续增量分析期间，已激活版本继续可读，受代码变化影响的对象标记过期；默认 Agent 查询不把已失效结论作为当前事实。新版本完成后再整体切换，未受影响的证据与知识允许复用。

一次分析固定读取源快照，不因工作树持续变化而反复重启。多仓项目使用各 Source 版本组成的版本向量；切换分支或 Workspace 时重新选择相匹配的知识，不能沿用上一分支的当前标记。对已落后的快照仍可完成分析并保存版本，但必须展示与当前代码的差异；无法判定受影响范围时保守标记未知，不声称仍然新鲜。

同一目标的替代分析使用递增的分析代际，只有当前目标 Run 可以自动更新该目标版本。旧 Run 晚完成只能保留历史成果；任务重试不产生新代际，新 Run 失败或取消也不自动恢复旧 Run 的激活资格。当前 Workspace 的 Source 选择另有版本校验，旧分支任务不能切回当前项目；后台完成不覆盖用户的停用或回退决定。

知识版本支持显式整版停用和回退。停用立即停止新请求默认使用该版本，保留历史、人工修订和原始材料查询。回退使用旧生成版本重新合并现有人工修订，先预览差异，再形成新的生效记录；无法关联的修订仍保留。旧版不因回退变新鲜，找不到适用版本时显示知识不可用。回退后保持所选版本，恢复自动更新需要操作者明确操作，不新增日常生成审核步骤。

知识自动可用不等于自动执行 Git 命令。本机激活版本独立于团队同步；操作者可以将版本保存为可共享项目文件，由现有 Git 流程提交。用户编辑后保存即可在本机生效，不需要为了使用自己的修订再走候选审批。

## 5. 用户修改与保存

完成后的知识提供直接编辑和保存。编辑器允许修改叙述说明、业务规则、流程步骤、代码位置和关系。保存校验数据完整性与当前编辑版本；正常保存不要求再次运行 LLM 或重新完成全项目分析。

结构化修改业务规则、流程步骤和关系时，编辑器直接更新共享知识对象，因此两个 Tab 同步生效。标题或布局调整不改变事实。自由正文修改立即保存为 Agent 可检索的人工修订，但不承诺无需 LLM 就能把任意自然语言完整转成结构化关系；受正文修订影响的旧事实与关系标为待复核，不能继续当作确定结论。用户也可以明确选择“追加说明”，保留原事实并增加独立的人类来源内容。后续局部语义对齐独立运行，不阻塞保存，不静默扩大人工编辑的含义。

每次保存形成独立修订，记录修改内容、修改来源、时间、基于的知识版本及被替代对象。自动分析结论与人工补充分别标识。用户改变了结论时，旧 Citation 不会自动证明新正文；仍保留原分析证据用于对照，新内容标记为人工修订，只有经过回查的引用才继续作为支持证据。缺少代码证据不阻止保存用户补充，也不把它标成模型已核验事实。

存储分别保留不可变的生成版本、人工修订和合并后的生效版本。人工修订立即参与后续知识查询，并且不会被后台分析静默覆盖。重新分析采用“原分析版本、人工修订、最新分析结果”比较：互不影响的修改合并，相同对象的冲突保留双方内容并提示用户处理。无法匹配到新对象的修订保留为待关联记录，不能丢失，也不能自动附到名称相似的另一个模块。重命名、移动、拆分和合并分别记录身份映射；标题、路径或 Run 内随机 id 不能单独决定身份延续。

人工修订与代码证据冲突时，保留修订正文和冲突标记；Agent 获得人工说明、新证据与冲突信息，不把人工修改等同于代码已经改变。页面支持查看修改历史、比较版本和恢复，恢复也产生新修订。多个页面或操作者并发保存使用版本校验，旧编辑不能覆盖更新后的内容。

人工修订的来源身份、语义待复核状态和源码新鲜度分别显示。修改过期对象不会清除其过期标记；人工正文仍可作为带源版本的说明查询，旧关系不能作为当前实现返回。项目切换、知识启用/导入和默认模型查询前检查 Source 状态；无法确认变更范围时先返回待检查提示，再做有界评估，不静默继续使用缓存的新鲜标记。

## 6. 深度分析与长期维护

大项目采用语言无关的全量 Catalog、有界材料读取、分层综合与针对项目问题的证据回查。AST、LSP、符号图和检索索引只辅助定位。跨文件、跨服务流程必须由模型阅读相关材料后建立，不把静态 import 当作业务调用关系。

分析对象包括本地代码、配置、测试、项目文档和带来源的业务补充。缺少关键业务背景时只针对具体问题向操作者询问，补充进入下一步分析材料。暂不增加外部平台连接器。

每个 Run 需要累计模型输入/输出 token 预算、暂停/恢复和消耗账本；任务原文字节预算继续独立存在。请求前预留额度，请求后按可获得的 usage 结算；重试和恢复不清零，未知用量不算零，也不把估算当作真实费用。预算不足时暂停，保留成果，扩额需要操作者确认。未变化对象和证据可缓存复用，但代码、规则或人工修订变化会使相应下游知识失效；失效范围包括引用它们的事实、流程和页面。应按实体与依赖更新，而不是对所有文件重新总结。

几 GB 正文和百万级文件数分别验收：前者需要有界原文读取和模型预算，后者还需要流式目录、分页读取及任务/对象级增量事务，不能每完成一个任务就加载或重写全项目快照。完整首次分析仍有与纳入正文规模相关的阅读成本；预算不够就保持未完成，不能用抽样或摘要覆盖率冒充完整理解。

Git 默认只共享选定版本及其完整必要依赖，不自动导出所有中间 Run；不变对象复用已有修订，保留人工历史与合并基线。导出预览文件数、总量与变更规模，超限明确停止，不截断依赖。小文件数量、重复分析后的增长和 Git 导入导出成本纳入规模验收，达到目标规模前再决定是否需要分片，不预先引入新存储引擎。

质量验收同时检查范围覆盖、核心业务问题、正常与异常流程、证据回查、未知/冲突展示、增量复用与成本。不承诺语义零误差，也不把文件数覆盖率作为项目业务理解的唯一指标。

## 7. 实施顺序与验收

1. 建立独立的记忆条目、知识对象、生成/人工/生效版本与完成报告模型；在同一纵切拆分入口、查询及召回，保留旧数据和审核历史，不追认旧知识卡具备完整 Wiki 资格。
2. 实现任务/对象级持久化、Run token 账本与问题驱动的跨模块分析，在 Claim/Citation/Coverage 基础上产出业务实体、规则、流程及两种视图。
3. 一起实现草稿查看、完成后自动激活、直接编辑保存、版本一致的双视图与 Agent 查询；不能把人工修订模型推迟到已发布知识之后再补。
4. 完成增量失效、重分析三方合并、分支/多 Source 选择与 Git 同步，用真实业务 fixture 验证编辑不会被重分析或团队更新覆盖。

最低验收包括：分析中草稿可见但不默认召回；完成后无需人审即可查询；必要阶段失败或耗尽预算不会激活；未知与冲突不会伪装成确定事实；保存后的新请求读到人工修订且两个 Tab 一致；保存无需 LLM；后续分析不覆盖修订；并发旧保存被拒绝；恢复历史可追溯；跨项目数据隔离；多语言业务流程能定位实现与测试；大项目暂停恢复与累计预算生效。

实施先交付单仓完整闭环，同时验证分析乱序、分支切换、人工修订与过期组合、整版停用/回退、材料交付证据、跨域关联和记忆详情。多 Source 与大规模 Git 验收分阶段完成；未达到的规模和能力明确标注，不因单仓演示成功就宣称全部实现。
